# Requested history, reflection, and preference review

Load only for an explicit request for this review. Ordinary wake handling,
startup recovery, and catch-up do not authorize transcript mining or preference
changes. Begin with current durable state and the provided context.

1. Establish the requested topic, project or named threads, and time window.
   If these cannot be inferred from the request, ask before searching outside
   the known scope. Use BB's supported evidence access, not Cursor paths.
2. For missing context, trace only the relevant commitments, decisions, source
   history, and outcomes. Cite provenance and label unresolved facts. Current
   records win over stale conversation claims. Do not search unrelated chats.
3. For reflection, connect each repeated correction to a concrete cause and a
   local proposal. Prefer an enforceable invariant where appropriate. Keep
   accepted, rejected, and unresolved proposals distinct. Review does not
   authorize edits, backlog filing, external messages, or other external writes.
4. For preference review, inspect existing instructions first. Separate repeated
   preferences from one-off requests, corroborate them across distinct scoped
   sessions, and cite the evidence. Propose deliberate corrections to existing
   instructions; do not create a hidden personal mode or duplicate rules.
5. Present findings and the proposed local change. Apply changes only under
   explicit authorization for those changes. Preserve imported native ownership
   and fidelity requirements. Any independent reviewer is assigned by the
   captain with the existing model and concurrency authority.
